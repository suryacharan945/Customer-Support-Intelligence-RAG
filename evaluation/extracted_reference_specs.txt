Introduction: From Prototype to Production 
Bringing Your RAG + MCP System to Life 
You've architected a sophisticated RAG (Retrieval-Augmented Generation) and MCP (Model-
Centric Prompting) system, and now it's time to make it accessible and ready for real-world 
use. This capstone project isn't just about completing a technical challenge; it's about 
bridging the gap between a functional prototype and a robust, deployable service. We'll 
focus on transforming your RAG + MCP logic into a well-defined API, packaging it for easy 
deployment, and preparing for its operational life. This involves not only coding but also 
strategic thinking about how your system will be used, maintained, and understood by 
others. Think of this as graduating your AI system from a research lab to a production 
environment, complete with all the necessary infrastructure and documentation. 
Our journey will cover four key pillars: building a performant API service, containerizing your 
application for consistency, planning for production readiness with deployment and 
monitoring in mind, and finally, crafting comprehensive documentation and a compelling 
presentation. Each step builds upon the last, ensuring that by the end of this module, you'll 
have a fully realized, production-ready AI system that you can confidently showcase and 
deploy. 
Building the FastAPI Service 
Building the FastAPI Service 
Exposing Your RAG + MCP Logic via API 
To make your RAG + MCP system accessible, we need a way for other applications or users to 
interact with it. An API (Application Programming Interface) is the standard way to achieve 
this. For this project, we'll leverage FastAPI, a modern, fast (high-performance), web 
framework for building APIs with Python 3.7+ based on standard Python type hints. FastAPI 
is chosen for its speed, ease of use, automatic data validation, and built-in interactive 
documentation, which will be invaluable for our capstone. 
We'll design API endpoints that mirror the core functionalities of your RAG + MCP system. 
Typically, this would include an endpoint for processing a query, which might involve steps 
like embedding the query, retrieving relevant documents, augmenting the prompt with 
retrieved context, and finally, generating a response using an LLM. We'll also consider 
endpoints for potential administrative tasks, such as updating the knowledge base or 
checking system status. 
Key Considerations for FastAPI: 
• Request/Response Models: Define clear Pydantic models for incoming requests 
(e.g., the user's query, any parameters) and outgoing responses (e.g., the generated 
answer, source documents, confidence scores). This ensures data integrity and 
provides automatic validation. 
• Asynchronous Operations: Many parts of a RAG system, especially external LLM calls 
and database lookups, can be I/O-bound. FastAPI's asynchronous capabilities 
(async/await) are crucial for handling these operations efficiently without blocking 
the server. 
## Page 2
• Dependency Injection: FastAPI's powerful dependency injection system allows us to 
manage resources like database connections, embedding models, and LLM clients 
cleanly, making our code more modular and testable. 
• Error Handling: Implement robust error handling to provide meaningful feedback to 
API consumers when things go wrong (e.g., invalid input, internal processing errors, 
external service failures). 
Let's imagine a core endpoint, perhaps /query, that accepts a user's question and returns an 
answer. We'll need to integrate our existing RAG pipeline components (retriever, prompt 
formatter, LLM) into this FastAPI application. 
FastAPI: Practical Implementation 
Coding Your RAG + MCP API

define an endpoint for our RAG system. Assume you have your RAG pipeline components 
(e.g., a RAGPipeline class) already implemented and ready to be integrated. 
First, ensure you have FastAPI and Uvicorn (an ASGI server) installed: 
pip install fastapi uvicorn[standard] pydantic

Containerizing with Docker 
Containerizing with Docker 
Ensuring Consistency and Portability 
Deploying applications can be notoriously tricky due to differences in environments – 
operating systems, installed libraries, configurations, and more. Docker solves this by 
packaging your application and all its dependencies into a standardized unit called a 
container. This container runs consistently regardless of where it's deployed, whether it's 
your local machine, a cloud server, or a Kubernetes cluster. 
For our RAG + MCP API, containerization means we can bundle our FastAPI application, 
Python runtime, and any system-level dependencies (like specific C libraries if our 
embedding models require them) into a single, portable image. This image can then be run 
as a container, providing an isolated and reproducible environment. 
Why Docker for this Project? 
• Environment Consistency: Guarantees that the application runs the same way in 
development, testing, and production. No more "it works on my machine" issues. 
• Dependency Management: All dependencies are declared in a Dockerfile, making it 
explicit and easy to manage. 
• Isolation: Containers run in isolation, preventing conflicts between different 
applications or system libraries. 
• Scalability: Docker containers are the building blocks for container orchestration 
platforms like Kubernetes, enabling easy scaling. 
• Simplified Deployment: Deploying a Docker container is as simple as running a 
command. 
We'll create a Dockerfile that instructs Docker on how to build our application image. This 
file will specify the base image (e.g., a Python image), copy our application code, install 
dependencies, and define how to run the application.

# Use an official Python runtime as a parent image 
FROM python:3.10-slim-buster 
 
# Set the working directory in the container 
WORKDIR /app 
 
# Copy the requirements file into the container at /app 
COPY requirements.txt . 
 
# Install any needed packages specified in requirements.txt 
# Use --no-cache-dir to reduce image size 
RUN pip install --no-cache-dir -r requirements.txt 
 
# Copy the rest of the application code into the container at /app 
# Assumes your FastAPI app is in an 'app' directory 
COPY ./app /app 
 
# Make port 80 available to the world outside this container 
EXPOSE 80 
 
# Define environment variable (optional, but good practice) 
ENV MODULE_NAME "main" 
ENV VARIABLE_NAME "app" 
 
# Run main.py using uvicorn when the container launches 
# Use 0.0.0.0 to bind to all network interfaces 
# Use --workers to specify the number of worker processes (adjust based on CPU cores)

# For production, consider a more robust entrypoint script 
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "80", "--workers", "4"] 
Explanation: 
• FROM python:3.10-slim-buster: Specifies a lightweight Python 3.10 image as our 
base. 
• WORKDIR /app: Sets the default directory for subsequent commands. 
• COPY requirements.txt . and RUN pip install ...: Installs Python dependencies. 
Copying requirements.txt first and installing allows Docker to cache this layer if 
requirements.txt doesn't change, speeding up builds. 
• COPY ./app /app: Copies your application code into the container. 
• EXPOSE 80: Informs Docker that the container listens on port 80 at runtime. 
• CMD [...]: The command to run when the container starts. We use uvicorn to serve 
the FastAPI application. The arguments specify the application instance 
(app.main:app means the app object in app/main.py), host, port, and number of 
workers. Adjust --workers based on your server's CPU cores for optimal performance. 
Building the Image: 
Navigate to the directory containing your Dockerfile in the terminal and run: 
docker build -t rag-mcp-api:latest . 
Running the Container: 
docker run -d -p 8080:80 --name my-rag-api rag-mcp-api:latest 
This command runs the container in detached mode (-d), maps port 8080 on your host 
machine to port 80 inside the container (-p 8080:80), and names the container my-rag-api. 
You can now access your API at http://localhost:8080.
